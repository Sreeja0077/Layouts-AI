1. Executive Summary
This document is the architecture blueprint for an enterprise office-layout generation platform used by a real-estate firm's sales and layout teams. It is written to be implementation-ready: every technology choice states the problem it solves, the alternatives considered, and the condition under which it should (or should not) be introduced.
The governing design rule is a strict division of authority:
AI proposes / understands
        +
Domain services interpret (catalog, terminology, business rules)
        +
Optimizer solves (placement, packing, constraint satisfaction)
        +
Geometry engine validates (collision, containment, clearance, egress)
        +
PostgreSQL/PostGIS stores authoritative state (the only source of truth)
The LLM never outputs final coordinates and is never the last check on physical validity. It extracts intent, resolves ambiguity through a formal clarification stage, chooses planning strategies, and interprets edits as structured, semantic actions. A deterministic Python geometry/optimization stack turns those actions into exact, validated placements. Every change is versioned as an append-only revision; nothing overwrites an approved plan.
The recommended starting architecture is a modular monolith (not microservices, not a multi-agent swarm), backed by PostgreSQL + PostGIS, Celery + RabbitMQ + Redis for async work, a single LangGraph-orchestrated AI workflow calling permission-scoped deterministic tools, and a React + Konva 2D editor. RAG and a dedicated vector database are explicitly deferred until there is a real corpus that justifies them. Section 3 gives direct, labeled answers to all 30 critical questions raised in the brief; the sections that follow justify each answer in depth.
2. Key Architectural Principles
Determinism owns geometry. Collision, containment, clearance, egress, and exact coordinates are always computed by Shapely/OR-Tools/PostGIS — never by an LLM, regardless of how capable the model appears.
The AI speaks in semantics, not coordinates. LLM output is a structured intent or constraint ("place near entrance", "keep these four") that a deterministic materializer resolves into geometry.
Every AI output is a typed, validated object. Pydantic/JSON-Schema-constrained structured output only; free-form text is never parsed downstream with regex or vibes.
Approved state is immutable. Publishing never overwrites; it creates a new pointer to a new revision. History is permanent and auditable.
Patches, not full snapshots, for edits. Small changes are represented as operations against a base revision, materialized lazily, snapshotted periodically for read performance.
Human approval gates are real gates, enforced server-side by role + workflow-stage checks — never assumed from the UI alone.
Modular monolith first. Strong internal module boundaries (domain-driven folders) give most of microservices' maintainability benefit without the operational cost; split out only what actually needs independent scaling.
Clarify only when it changes the outcome. If a safe default exists and the requirement is materially unambiguous, proceed silently; never invent a value that would change feasibility or the client's expectations.
Open-source and provider-agnostic by default. LiteLLM-style abstraction over the LLM provider, IfcOpenShell over proprietary BIM SDKs where possible, Postgres extensions before adding new services.
Testability is a first-class design constraint, not an afterthought — geometry, AI, ingestion, and workflow logic are each testable in isolation, most of them without any LLM call at all.
Explainability by construction. Because placement is rule-based and the AI's contribution is a small set of typed decisions, every suggestion can be explained by walking the same structured trail a human would.
Introduce infrastructure only when a concrete, current problem requires it — not because it is "standard architecture" for AI systems in general.

Append-only revisions with explicit draft/published pointers per floor plan; approved revisions are never mutated. See §21.

The API always resolves the floor plan's current_working_revision_id server-side; clients never guess or cache a stale pointer. See §21.

How do revisions and patches work?
Each revision = base revision + ordered operation list; materialized snapshots are cached and periodically persisted, always reconstructible from patches. See §21.
19
How should approval work?
A 4-role sequential state machine (Sales Exec → Layout Exec → Layout Manager → Sales Manager) with server-enforced stage/role permissions. See §22.
20
What happens when someone edits an approved plan?
A new draft revision is created from the approved one; the approved version is untouched until the new revision completes its own approval cycle. See §21.
21

Celery from day one. BackgroundTasks is insufficient for retryable, trackable, business-critical jobs like ingestion and generation. See §25.
22

RabbitMQ as the broker (durable, acknowledged delivery) plus Redis for cache/result-backend — both from the start, not staged. See §25.
23
Is gRPC necessary?
No. REST + WebSocket (for job/progress updates) covers every current need. See §24.
24
Is batching necessary?
Selectively: embedding generation and bulk BIM-object inserts benefit; per-request LLM calls and candidate validation should not be batched. See §25.
25
What security/encryption is actually needed?
TLS everywhere, platform-managed encryption at rest, strong password hashing, RBAC + object-level ACL, audit logging — not custom application-level crypto. See §28.
26
What monitoring is actually needed?
Structured logs, error tracking, and basic queue/worker metrics for MVP; full distributed tracing and AI cost dashboards later. See §30.
27
What privacy/compliance concerns matter?
Personal data in voice notes/client details (India's DPDP Act framing), retention limits on raw audio, and care with any data sent to an external LLM provider. See §29.
28
What should NOT be built in the MVP?
Microservices, Kubernetes, gRPC, a dedicated vector DB, RAG, multi-agent swarms, a 3D engine, and LLM-computed coordinates. See §36.
29
Biggest technical risks?
BIM export quality variance, LLM structured-output reliability, concurrent-edit conflicts, and freehand-selection geometry edge cases. See §35.
30
Where would a naïve AI architecture fail?
Letting the LLM emit coordinates directly, skipping the clarification gate, regenerating whole plans on tiny edits, and treating vector search as authoritative state. See §35.

4. Recommended End-to-End Architecture
A modular monolith backend with clearly separated domain modules, a pure-Python AI package (LLM orchestration only), a pure-Python geometry/optimization package (no LLM, no web framework), and a React frontend. This gives most of the maintainability benefit of microservices — enforced boundaries, independent testability — without distributed-systems overhead the team does not yet need.

4.1 Why a Modular Monolith and Not Microservices
The domain is a single cohesive workflow (requirement → catalog → geometry → revision → approval) with strong data coupling; splitting it into services would mean constant cross-service transactions to keep revisions and approvals consistent.
Team size and current scale do not require independent deployability of each module; the cost (service discovery, distributed tracing, network failure handling) would exceed the benefit today.
Module boundaries (domain/requirements, domain/catalog, domain/layout, domain/geometry, domain/optimization, domain/revisions, domain/approvals) are enforced in code (no cross-module imports except through public interfaces), so extraction later, if ever needed, is a refactor, not a rewrite.
The one component that legitimately benefits from independent scaling early is the worker pool (geometry/optimization and AI calls are CPU/latency heavy) — and Celery already gives that without a service split.

[REQUIRED — MVP and near-term]  Use react-konva. A real office floor plan has, at most, low hundreds of interactive furniture objects per view — well inside Konva's comfortable performance envelope — while its built-in Transformer, React bindings, and hit-testing eliminate a large amount of custom editor engineering that would otherwise be needed for drag/rotate/resize/snap interactions. 7. Frontend Geometry vs Backend/Shapely (the Turf.js Question)

[REQUIRED]  Treat IFC (not RVT) as the canonical open, parseable interchange format. The Layouts Team exports it using Revit's free built-in exporter.
[LATER / OPTIONAL]  Autodesk Platform Services only if/when the organization wants to eliminate the manual export step through automation and is willing to pay for it — not needed for MVP or for correctness.
8.2 What is lost in RVT → IFC, and what must be preserved
Lost or degraded: some parametric family behavior (the family's editable parameters, not just its instance geometry), certain proprietary annotation/dimension styling, worksharing/phasing metadata not mapped to IFC property sets, and some MEP-specific parametric constraints.
Preserved well (with a correct IFC4 Reference View export): wall/door/window/column geometry, room/space boundaries, basic properties, and object hierarchy.
Must be explicitly preserved by the ingestion pipeline: the original .rvt file (archival), the IFC GlobalId of every element (for stable-ID mapping across re-exports), export timestamp and exporter/Revit version, and the project base point / survey point / unit system so world coordinates are unambiguous.
8.3 IFC Parsing
IfcOpenShell (LGPL) is the real, actively maintained open-source toolkit for this — it genuinely parses IFC geometry and properties in Python and is the correct choice here; it should not be confused with a hypothetical RVT parser.
Layouts Team exports IFC from Revit (free)
    -> upload to object storage
    -> ingest_worker: IfcOpenShell extracts walls/doors/windows/columns/spaces/
       properties, maps IFC units to millimetres, captures project base point
    -> internal object IDs generated, each cross-referenced to its IFC GlobalId
    -> Floor JSON (draft) + confidence flags -> Layouts Team verification UI
    -> publish
8.4 Stable IDs and Re-Ingestion / Revisions of the Source BIM File
IFC GlobalId is stable across re-exports of the same underlying Revit element, provided the element itself was not deleted and recreated in Revit — this is the join key used to reconcile a new IFC upload against the existing internal model.
On re-ingestion, a diff pass matches elements by GlobalId: unchanged elements keep their internal ID and any layout work built against them; changed elements (moved wall, resized room) are flagged; new elements are added; elements no longer present are flagged as removed, not silently deleted, because furniture already placed against them may need reconciliation.
A structural change that conflicts with existing layout work (e.g., a wall that had furniture placed against it moved) surfaces as a manual reconciliation task for the Layouts Team before the new FloorPlanSourceVersion can be published — this is a deliberate human checkpoint, not an automatic merge.

9.1 Storage: JSON, PostGIS, or Both
[REQUIRED — hybrid, not either/or]  Store the rich object semantics (catalog reference, rotation, provenance, lock state, metadata) as JSONB on each row, and generate a PostGIS geometry column from the same row (trigger or application-layer write-through) purely for spatial querying — containment, intersection, nearest-neighbor, GiST-indexed. JSONB alone cannot efficiently answer "what intersects this region" at scale; PostGIS alone is awkward for arbitrary semantic metadata. Using both from the same write avoids the two ever disagreeing, since PostGIS geometry is always derived from the JSONB record, never edited independently.
Example placed-object record:

10. Furniture Catalog & Semantic-to-Physical Mapping
The system must never require the sales executive to manually decompose "4 executive desks" into its components. A catalog/bundle resolver handles that translation deterministically, with the LLM only supplying the raw phrase and category guess.
EXECUTIVE_DESK_BUNDLE (catalog_item: cat_exec_desk_180)
    ├── desk/table            (1800mm x 800mm)
    ├── executive chair       (650mm x 650mm)
    ├── front clearance       900mm
    ├── rear clearance        0mm (against wall)
    ├── side clearance        0mm
    └── orientation rule      "faces away from wall"
10.1 Resolution Pipeline
Exact/alias lookup — a synonym table maps "executive desk", "exec desk", "director's table" etc. to one canonical catalog_item_id. This handles the large majority of real phrasing cheaply and deterministically.
Fuzzy/embedding fallback — if no alias matches, an embedding-similarity search over catalog descriptions (via pgvector) proposes the closest canonical item with a confidence score.
Confidence threshold gate — above threshold, resolve silently; below threshold, this becomes a blocking clarification ("Did you mean Professional Desk or Office Desk?") rather than a silent guess.
"Professional desk" vs "office desk" vs "6 seater" vs "manager cabin" vs "meeting room" are all resolved the same way — through this catalog/alias/embedding pipeline, never memorized or hardcoded in a prompt.
Example resolution output fed to the requirement/optimizer stage:
{
  "raw_phrase": "6 Professional Desks or Office Desks",
  "resolved_catalog_item_id": "cat_prof_desk_140",
  "resolution_method": "alias_exact",
  "confidence": 0.97,
  "quantity": 6
}

13. LangGraph Evaluation
[USEFUL FOR MVP, not strictly required]  LangGraph is justified specifically because this workflow must pause for a clarification answer that may arrive minutes or hours later (the sales executive is with a client, may close the laptop, may resume the next day), and again pause after presenting candidates until one is selected. LangGraph's built-in checkpoint persistence handles this pause/resume cleanly. A hand-rolled state machine on top of Postgres is a legitimate alternative with identical explainability and zero extra dependency, at the cost of writing that persistence layer yourself. Recommendation: use LangGraph, but wrap it behind an internal WorkflowEngine interface so it is swappable without touching node logic.

18. Layout Optimization Architecture
This is the technical core of the system and is never delegated to the LLM. The pipeline below is designed explicitly for irregular and concave regions, not just rectangles.
Region polygon (possibly concave/L/U-shaped)
    - subtract fixed obstacles (walls, columns, doors' swing arcs)
    - subtract required clearance buffers around fixed objects
    -> Free-space polygon / MultiPolygon (Shapely)
 
Candidate generation:
  (a) Strategy templates: perimeter, two-row, clustered, cabin-near-entrance,
      cabin-at-rear, circulation-focused — each a parameterized seed layout
  (b) Grid-sampled anchor points inside the free-space polygon at
      furniture-module resolution, filtered to fully-contained placements
  (c) For item counts <~60: OR-Tools CP-SAT formulates exact placement as a
      constraint-satisfaction problem (positions on a coarse grid, non-overlap,
      clearance, aisle-width constraints) -> guarantees hard-constraint validity
  (d) For larger item counts: heuristic shelf/guillotine packing adapted to the
      free-space mask, used standalone or as a fast seed for CP-SAT refinement
 
Circulation/egress check:
  - build a navigable free-space graph (grid or visibility graph)
  - verify every seat has a path to an exit meeting minimum aisle width
  - reject candidates that fail
 
Diversity + selection:
  - cluster surviving candidates by (strategy tag, spatial signature)
  - score (seats achieved, circulation ratio, power reach, symmetry)
  - return top 3-5, one per distinct strategy cluster where possible

19. 3–5 Candidate Generation
Candidates must represent genuinely different planning strategies, not coordinate jitter of the same idea. Strategy templates used as seeds:
Perimeter arrangement — furniture hugs the walls, open center for circulation.
Two-row / back-to-back clusters — dense, common for open-plan desk banks.
Manager cabin near entrance — cabin-first placement anchored to the entrance side, remaining desks packed into leftover free space.
Manager cabin at rear — cabin-first placement anchored away from circulation noise.
Central circulation-focused — wider central aisle, furniture pushed to both sides, prioritizing walking comfort over density.
Every candidate, regardless of strategy, passes the same hard-constraint validation gate (collision, containment, clearance, egress) before being eligible for return; candidates are then deduplicated by spatial signature so the 3–5 shown are meaningfully distinct.

20.1 Reference Resolution
Natural references are resolved by a small, explicit resolver rather than left to model guesswork:
"this desk" / "these four" — resolved against the last object(s) the user selected in the editor UI or most recently mentioned in the conversation (recency heuristic, with the selection explicitly passed alongside the instruction).
"the manager cabin" — resolved by unique-type match if only one exists; if multiple, this becomes a blocking clarification rather than a guess.
"left side" / "window side" — resolved geometrically against stored floor-plan orientation metadata (which wall segment is tagged as the window wall; screen-left is mapped to world coordinates using the current view's orientation).
"the room near the entrance" — resolved spatially: candidate rooms/regions ranked by proximity to the entrance object, top match used unless ambiguous (two rooms nearly equidistant), in which case it becomes a clarification.

21. Versioning: Working vs Approved Revisions
This is the most business-critical mechanism in the system and is designed explicitly around the brief's worked example.
V12 (approved, published)
  Sales Exec creates draft -> V13 (working)
  Sales Exec selects AI candidate 3 -> V13.1 (working)
  Layout Executive opens the floor plan
      -> API resolves floorplan.current_working_revision_id -> V13.1 (always correct, never guessed)
  Layout Executive edits -> V13.2 (working)
  Layout Manager approves V13.2 -> approval recorded against revision_id=V13.2, content_hash=H1
  Sales Manager approves V13.2 -> floorplan.current_published_revision_id = V13.2
  V12 remains permanently retrievable; nothing was overwritten
 
  Later: someone edits the approved plan
  New draft created from V13.2 -> V14 (working) -> ... -> approved -> V14 published
21.1 Revision & Patch Model
Each revision = a base_revision_id plus an ordered list of operations (ADD / REMOVE / MOVE / MODIFY / RESIZE_REGION). This is event-sourcing-lite, not full event sourcing — it is scoped to layout objects, not the whole system.
A materialized snapshot (the fully resolved object list) is cached per revision for fast reads, but is always reconstructible by replaying operations from the nearest prior snapshot — snapshots exist for performance, not as the source of truth.
Snapshots are taken at natural checkpoints: every N operations, and always at stage transitions (submit, approve, publish), so reconstruction never requires replaying an unbounded chain.
Optimistic concurrency: each revision row carries a version_no; a write must supply the expected version_no (ETag-style) or receives a 409 conflict, surfaced to the client as a merge/retry prompt rather than a silent overwrite.
Concurrent-edit conflicts (e.g., Sales Exec and Layout Exec editing at the same moment) are handled per-object where possible — two edits to different objects both apply; two edits to the same object trigger the 409 path.
The approval-revision link is explicit and strict: an Approval row references an exact revision_id and a content hash. If the underlying revision changes after being submitted for approval, the approval is automatically invalidated and the workflow state reverts to DRAFT, requiring resubmission — this prevents anyone approving content that quietly changed underneath them.
Rollback creates a new revision that copies an old snapshot's operations forward; history is never mutated, only extended.
Version comparison reuses the same diff engine that powers the frontend's visual diff: two materialized snapshots are compared object-by-object (added / removed / moved beyond a distance threshold).
21.2 How the Frontend Always Loads the Right Version
The frontend never caches or infers "the latest revision" — every load calls the floor plan endpoint, which returns current_working_revision_id and current_published_revision_id explicitly. This single server-side pointer is what guarantees the Layout Executive sees the Sales Executive's latest work (V13.1) rather than the older approved version (V12), directly answering the brief's central versioning concern.

25. Async Jobs: Celery / Redis / RabbitMQ
Precisely, what each component is: Celery is the task-execution framework (defines tasks, retries, routing); it needs a message broker to deliver tasks to workers and, optionally, a result backend to store return values. RabbitMQ and Redis can each play the broker role; Redis additionally serves well as a cache and as the result backend regardless of which broker is chosen.

[REQUIRED from the start — Celery + RabbitMQ + Redis, not staged]  BackgroundTasks (FastAPI's built-in fire-and-forget) is explicitly insufficient here: BIM ingestion, AI generation, and optimization are long-running, must survive a worker crash, must be retryable, and must report progress — none of which BackgroundTasks provides. Given that, Celery is required immediately, not something to add "later." Between brokers: this system's async jobs are business-critical (an ingestion job or a generation job silently disappearing is a real product problem, not a minor inconvenience), so RabbitMQ's durable, acknowledged delivery is the correct default from day one rather than starting with Redis-only and upgrading under pressure. Redis is used alongside it as the cache and Celery result backend — this is not redundant, the two serve different roles.

26.1 Property / Invariant Tests (Hypothesis)
Furniture never extends outside the usable region, for any randomly generated valid region and requirement.
Fixed furniture (keep_flag / locked) never moves across any optimizer run.
Requested quantity is either satisfied exactly or the candidate is explicitly flagged as partial with a stated reason — never silently short.
No candidate returned to the user contains an illegal hard-constraint collision.
Clearance thresholds are maintained around every placed object.
An approved revision's materialized snapshot is byte-for-byte identical no matter how many times it is reconstructed from its patch chain.
Modifying an approved revision always produces a new revision; the approved row's content_hash never changes.
An approval becomes invalid the instant its linked revision's content_hash changes.
AI tests are run two ways: a recorded/replayed corpus in CI for determinism and speed, plus a smaller live-model nightly run against the actual configured Ollama cloud models to catch provider/model drift before it reaches production.

28. Security & Encryption
TLS/HTTPS everywhere, including internal service calls where practical — required, not optional, even for an internal enterprise tool, because it handles client-identifiable data and commercially sensitive floor plans.
Encryption at rest via the managed Postgres/object-storage platform's built-in encryption — sufficient for this data sensitivity level; do not build a custom application-level encryption layer on top, which mainly adds complexity and key-management risk without a corresponding real threat it uniquely addresses.
Password hashing with argon2 or bcrypt; short-lived JWTs with refresh tokens; secrets in a manager (not .env files in production).
RBAC for the four workflow roles plus object-level access control scoped to project/client, since multiple clients' floor plans and requirements coexist in one system and must not cross-leak between sales teams handling different accounts.
Audit logging of every state-changing action (already modeled as the audit_log table in §23) — this is a security control as much as a compliance one, since approvals carry real business weight.
AI tool permission boundary (detailed in §38.9): the AI layer is only ever given read + propose-scoped tool calls; it cannot directly write to the database, delete data, publish a layout, or change permissions.
[NOT RECOMMENDED]  Custom application-level encryption schemes beyond what the database/storage platform already provides — this adds engineering and operational risk (key rotation, recovery) that is not justified by this system's actual threat model.

Data residency: if any client contractually requires India-only storage, this affects the choice of hosting region for Postgres/object storage and, separately, whether the LLM provider processes data outside that region — these are two independent constraints to check.
Backups should follow the same access-control and encryption posture as primary storage; backup retention should have an explicit, documented policy rather than growing indefinitely by default.

31. Performance
Targets below are labeled as assumptions to validate against real usage, not guarantees.
Frontend rendering: Konva comfortably handles the expected object count per view (low hundreds); target 60fps drag/rotate interaction on a mid-range laptop [assumption].
Coordinate transforms: kept trivial (linear screen-to-world mapping); no measurable cost expected.
Client-side geometry (area/perimeter preview): O(n) shoelace-formula computation on stroke points, negligible cost even for a few thousand points [assumption].
Database queries: PostGIS GiST indexes keep containment/intersection queries sub-100ms at expected catalog and object volumes [assumption, to be load-tested].
BIM ingestion: dominated by IfcOpenShell geometry extraction time, which scales with file complexity; run as an async Celery job so it never blocks the API regardless of duration.
Optimization runtime: bounded per request (a hard wall-clock budget, e.g., a few seconds for CP-SAT before falling back to the heuristic packer's best result) so a pathological region/requirement cannot monopolize a worker.
AI latency: each LLM call is async and surfaced via WebSocket progress updates rather than a blocking HTTP request, since cloud model latency is variable and out of this system's direct control.
Caching: Redis caches parsed floor JSON and catalog lookups to avoid repeated DB/geometry recomputation for read-heavy views.
Worker scaling: separate Celery queues per job type (ingest/speech/ai/geometry) so a burst in one does not starve the others; horizontal worker scaling by queue depth once load data justifies it.

33. Production / Scale Architecture
What changes as the platform grows — introduced when a concrete need appears, not preemptively:
Geometry/optimization workers become an independently scaled pool (still Celery workers, potentially on dedicated compute given their CPU profile) if generation volume grows enough to need it.

Qdrant introduced only if the knowledge base or catalog embeddings genuinely outgrow pgvector's comfortable range (§16).
RAG introduced only once a real corpus of design standards / historical approved layouts exists and has been curated (§15).
OpenTelemetry tracing across the AI workflow and geometry pipeline once multiple workers make log-only debugging insufficient.
Horizontal API replicas behind a load balancer; autoscaling workers by per-queue depth.
CDN for static frontend assets.
Multi-region considered only if a specific client data-residency requirement or genuine latency need for a geographically distant office demands it — not speculatively.

39. Final Summary
The architecture is built around one non-negotiable boundary: the AI understands and proposes, deterministic Python decides geometry. Everything else in this document follows from protecting that boundary — structured outputs instead of free text, a materializer/compiler between semantic intent and coordinates, permission-scoped AI tools, append-only revisions with explicit working/published pointers, and a server-enforced multi-role approval chain.
The recommended starting stack deliberately avoids fashionable but premature infrastructure: no microservices, no Kubernetes, no multi-agent swarm, no RAG, no dedicated vector database. It instead invests early in the things that are hard to retrofit — the canonical data model, the deterministic geometry/optimization core, the revision/patch system, and the approval state machine — because correctness and auditability in those layers are the actual foundation of a system a real-estate firm can trust for client-facing work.
The 39 sections above, together with the folder structure in §27 and the phased plan in §34, are intended to be detailed enough for an engineering team to begin Phase 0 directly from this document.
